长期科研人机协作工作台：实施交接包
版本 1.0.0　设计基线 2026-11-25

一、用途
本包用于从零设计并实现一套独立、本地优先的科研人机协作工作台。
目标场景是研究者与 Codex、Claude Code 等工具持续数月的日常协作。
核心任务是保存项目认识、解释实际进展、追踪证据和失败探索，并让研究者掌握路线与工作节奏。
本包是设计与合同，不含已经运行的产品，也不包含真实用户的研究资料或凭证。

二、内容
specification.html：完整方案，可离线浏览，包含目录、表格、嵌入图片和来源链接。
specification.txt：相同方案的纯文本版本，适合搜索和交给实现AI，保留来源URL。
contracts/README.txt：先读此文件，理解数据真源、权限与版本约定。
contracts/domain.schema.json：JSON Schema 2020-12，18类领域实体与36个定义。
contracts/core-api.yaml：OpenAPI 3.1，35个HTTP操作；21种领域命令通过候选变更提交。
contracts/example-project.json：虚构实体快照；事件数组为节选，不能重放完整项目历史。
contracts/acceptance-cases.json：60个实现后必须执行的验收场景。
sources.json：50组一手来源登记、类型、用途与核验日期。
diagrams/：3幅精确设计图的PNG、SVG及Graphviz DOT源文件。
validation_summary.json：本次实际执行的静态检查，以及尚未执行的产品验证。
MANIFEST.sha256：交付文件内容摘要，用于校验包内文件。

三、建议阅读顺序
科研负责人：第1、3、6、7节了解场景与日常流程；第4、5、8节理解节点、证据、审阅、授权与阅读规范。
产品设计者：补读第2节调研、第16节理解与控制权评估；先制作第17节阶段A样机。
开发者或实现AI：完整阅读方案，之后先读合同README，再核对Schema、OpenAPI、示例与验收场景。
第9–15节用于实施查询；第17节规定阶段交付，第18节提供来源与继续核验要求。

四、交给实现AI的任务方式
先要求实现者准确复述产品范围和关键不变量，不立即一次性生成整个应用。
每次分配一个可运行、可审阅的闭环，附需求编号、相关章节、合同、输入例子及验收条件。
第一个闭环建议为：打开历史研究节点，看到自包含背景、方法与证据，能够定位原始来源。
随后实现真实版本与授权，再连接一个Harness，最后扩展长期检索及第二连接器。
普通实现细节自主处理；涉及产品范围、权限、主张含义或合同变更时保存具体设计决定。

五、不能违反的规则
1. 一次实验运行成功、研究单元结束、主张有证据支持、用户审阅通过与允许执行是不同状态。
2. 模型可以提交候选变更，不能批准自身建议或伪造用户授权。
3. 已有有效授权可复用；旧快照或历史用户消息不能重新激活撤销或到期的授权。
4. 点击图节点只改变浏览位置，不改变正在执行的会话绑定。
5. 从历史快照继续默认建立新分支，保留当前文件、后续反证和真实恢复范围。
6. 阅读说明必须补足背景；模型上下文与人的说明分开生成，并引用精确对象版本。
7. 一个本地事务服务管理有效项目状态；Markdown、JSONL和界面图不是平行可写真源。
8. 不把来源相关性当成因果，不把模型自报完成当成实际验证。
9. 接口未知或不支持时明确降级；不通过提示词或假事件伪装控制成功。
10. 无模型连接仍可浏览、人工管理、检索和导出已有项目。

六、验证范围
本次已校验领域Schema、虚构示例、OpenAPI引用和部分结构约束，以及非法输入的拒绝样例。
未运行实际服务、真实Harness控制、数据库事件重放实现，也未开展真实人类理解实验。
60个验收场景是未来产品必须通过的要求，不是本次已经通过的产品测试。
论文和仓库文档用于机制调研，不能等同所有工具已安装、已审计或长期试用。

七、修改与发布
合同与正文出现冲突时必须同步修订，不能由实现者静默选择一种解释。
采用第三方代码之前固定提交或发行版本，复核许可证、数据处理位置和真实兼容性。
包含新字段、命令或状态语义的修改必须提升合同版本，提供迁移与回归测试。
