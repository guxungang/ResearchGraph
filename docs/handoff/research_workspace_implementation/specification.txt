长期科研人机协作工作台产品与实施方案

版本 1.0　｜　设计基线日期 2026年11月25日

适用对象：产品设计者、软件开发者、科研负责人、承担实现任务的人工智能编码助手。

阅读说明

本方案规定一套独立、本地优先的科研协作工作台。研究者通过 Codex、Claude Code 等智能体工具开展持续数月的科研工作，工作台负责保存项目背景、组织探索历史、解释实际进展、管理决策及证据，并提供可执行的干预入口。研究者仍然通过正常的人机对话推进项目。

系统首先交付本地 Web 应用，使用同一前端和本地服务逐步封装桌面应用。参考实现暂定以 macOS Apple Silicon 为首个验收平台；这是控制首版测试范围的工程假设，不是对使用者设备的判断。开发团队可在开工时更改参考平台，但必须记录决定并同步兼容矩阵。桌面封装和其他操作系统按后续兼容矩阵验收。系统必须能在没有模型连接的情况下浏览历史、编辑研究记录、管理分支及恢复项目背景。

本方案包含产品边界、研究与项目比较、阅读体验规范、领域模型、集成边界、数据一致性、实施接口、测试和发布条件。文中“必须”是验收要求，“建议”是可经记录调整的默认设计，“后续”表示不属于首个稳定版本的必备范围。外部项目能力与研究发现附来源编号；阈值、架构取舍、界面要求和实施顺序是本方案的设计决定，不是文献已经证明的结论。

配套实施合同包含数据结构、核心接口、可验证示例及验收用例。字段和接口拼写以合同为准；产品含义、权限约束和验收条件以本方案为准。出现冲突必须修订版本并同步更新合同，不能由实现者静默选择一种解释。示例中的科研项目、结果与文件名均用于说明系统行为，不代表已经开展或完成的真实实验。

1 产品目标与范围

1.1 需要解决的工作问题

复杂科研项目通常经过问题定义、文献比较、方法设计、代码实现、实验验证、结果解释和论文写作。各项活动可以并行，也会反复返回早期判断。几个月内形成的数百次人机交互，包含大量不应丢失的背景：为什么选择某种方法、哪些条件使原方案失效、一次实验究竟检验什么，以及哪些结论仍然没有证据。

如果这些信息只存在于聊天记录，研究者既难以恢复整体认识，也容易把执行者的工作总结当成实际进展。模型可能继续优化一个局部问题，而研究者直到最后检查代码或论文时才发现方向已经改变。系统要同时改善历史知识保存、工作透明度、人的理解和项目决策，不能只增加一个聊天检索框。

产品的核心结果是：研究者在任何工作节点，都能用低成本回答“正在解决什么问题、为什么选择这条路线、真正完成了什么、依据在哪里、哪些判断还不成立、下一步有什么选择”。

1.2 第一版用户与场景

第一版服务单个科研负责人，可以管理多个彼此隔离的项目。项目内容包括文献、研究笔记、代码仓库、实验配置、结果文件和论文版本。学生或合作者的工作可以作为带作者来源的资料导入；多人同时编辑、远程角色权限和团队云同步不属于第一版。

用户可以继续在原有 Harness 中对话，也可以从工作台启动一个受管理的会话。Harness 指围绕模型提供对话、工具执行、文件访问、权限和会话管理的运行程序，例如 Codex CLI 或 Claude Code。工作台通过正式接口连接 Harness，不假设能够读取模型未公开的内部推理。

1.4 边界

系统不以无人值守连续执行数十小时为核心目标。用户可以授权单项工作自动完成，但任何长循环都应有明确工作范围和退出条件。系统不替研究者判断论文一定可发表，不将自动审查当成科学正确性证明，也不承诺完整观察所有外部程序。

系统不默认上传整个项目、不扫描用户全部会话、不自动公开成果。联网模型可以是用户配置的外部服务；“本地优先”表示项目数据和状态由本机掌握，不表示调用外部模型时不存在数据传输。界面必须说明每次分析的提供方和发送范围。

1.5 阅读路径与技术词汇

科研负责人优先阅读第1、3–8、16–17节，以理解工作方式和验收结果；产品设计者再阅读第2节研究依据；开发者需完整阅读，并将第9–15节与配套合同一起使用。按角色选择阅读顺序不改变任何必须要求。

2 调研方法与证据边界

2.1 调研问题

调研按五条主线组织：长期交互记忆、非线性探索与来源追踪、可理解的人机交互、任务与决策治理、Harness 与科研工具集成。选择标准是机制是否能解决本产品的具体问题，而不是项目热度或功能数量。

来源优先采用原论文、作者项目页、官方仓库和官方接口文档。研究原型的用户实验、维护者的功能声明、标准规定和本方案的工程推断分别处理。仓库页面核验只能证明当前文档公开描述了某项能力，不能代替安装测试、源码审计或数月的实际使用。

覆盖范围包含代表性研究与项目，但不声称穷尽全部工具。调研截止日期为2026年11月25日。实施时必须为拟采用依赖固定版本或提交号，记录许可证与接口兼容测试结果，不能把本方案日期之后的变化视为已经验证。

2.2 长期记忆研究

LongMemEval。 该基准分别评估信息提取、跨会话推理、时间推理、知识更新和无法回答时的保留判断，并把记忆处理拆为索引、检索和阅读。这说明只测试“能否找到旧消息”不够。工作台还要判断旧决定是否仍有效、证据是否足以回答，以及何时应该显示未知。[S01]

LoCoMo。 该研究通过较长的多会话对话评估问答、事件总结等能力，揭示时间和因果关系理解的困难。它适合作为记忆组件的补充测试，不能直接衡量科研人员是否理解方法、是否及时发现项目偏航。[S02]

LongMemEval V2。 该2026年预印本研究从大量智能体轨迹中获取环境经验，同时考虑正确率和查询延迟。工作台可借鉴“返回紧凑证据供后续判断”的接口形式。该任务以环境经验为主，不应把其分数视为科研工作效率。[S03]

Hindsight。 研究将外部事实、智能体经历、综合实体摘要和演化观点区分，并提供保存、召回、反思操作。工作台应借鉴信息性质分离，但不能把系统命名为“事实”的记录直接认定为真实；原始来源、验证范围和人工审阅仍需独立维护。[S04]

上下文工程。 Anthropic 的技术文章讨论压缩、外部笔记和独立子任务上下文。工作台据此采用分层、按需构建背景，而不是无限扩张统一摘要。具体检索预算和保存策略需要通过本产品的中英文科研语料评测。[S05]

2.3 人机交互与可视分析研究

Sensecape。 系统以多层抽象和画布帮助用户在探索与组织信息之间切换。其研究支持非线性导航的价值，但原实验规模较小、任务较短，不能证明数月科研效率提升。更多分支也可能增加认知负担。本产品因此采用稳定二维布局、可折叠层级和独立的收束提示，禁止以节点数量评价进展。[S06]

ScholarPhi。 该系统在术语与数学符号出现的位置提供解释，直接针对读者缺少前置定义的问题。工作台借鉴位置相关、版本相关的术语解释；理解结论必需的背景应直接写出，不能全部藏进悬浮提示。[S07]

Scim。 该系统支持按内容类型和密度进行科学论文扫读。工作台借鉴可调阅读密度的思想，自行定义“概览、方法、实现、原始证据”四种阅读深度，并允许按问题、结果和局限筛选。快速扫读不能替代方法与结果核验。[S08]

AI Chains 与 ChainForge。 前者研究可编辑中间结果和模块化交互，后者提供提示词与模型实验的可视比较。可借鉴的机制是局部检查、共同输入下的方案对比和修改后的下游影响展示。科研路线图不应强制变成固定的自动执行链。[S09][S32]

认知干预研究。 Buçinca 等研究显示，某些要求用户主动思考的交互可以减少错误采纳，同时带来操作负担。工作台只在重要路线选择、证据冲突等节点提供可选择的反证检查，不为每次修改增加确认关卡。[S10]

HAX 交互准则与目标反思研究。 能力边界、容易纠正、可撤销和用户控制应成为基础交互。关于会议目标反思的研究提示，被动展示较少打扰，主动干预更容易触发行动但可能中断流程。工作台默认使用侧栏与待关注列表，只有明确的重要冲突才主动提醒。[S11][S12]

知识工作与批判性思考。 相关调查将对生成式AI的信心与自述思考投入联系起来，但属于观察和自述证据，不能推出因果。对本产品更合适的评估是用户能否解释方法、核实依据和发现错误，而不是单独追求信任或满意。[S13]

2.4 科研来源追踪与版本管理

VisTrails。 其探索工作流历史、版本树和结果比较提供了重要先例：方法版本与实际运行必须分开。恢复某个方法版本不代表恢复某一次实验。本方案借鉴其概念，不把历史版本文档视为当前应直接采用的技术栈。[S14]

W3C PROV。 该来源模型区分实体、活动和责任主体，并表达使用、生成与派生关系。工作台将论文片段、代码版本和实验结果视为实体，运行与分析视为活动，人和工具视为责任主体。第一版使用关系表实现所需子集，不要求引入专用图数据库。来源可追溯不等于结论正确。[S15]

2.6 复用策略

第一版独立定义领域模型、权限、状态转换和阅读规范。历史采集优先使用官方接口，必要时通过适配器利用 Sessions 等工具的导出。Planning with Files、ProjectMem、GSD 和 Superpowers 主要作为设计参考，不要求用户同时安装整套工作流。

通用记忆服务作为可替换的检索组件。只有本地检索基线在真实科研问题上出现明确瓶颈时，才接入 Hindsight、Graphiti 或 Mem0。检索组件不能拥有用户批准权限，也不能直接修改科学主张的有效状态。

代码版本直接使用 Git；实验追踪和文献管理采用独立适配器，可后续连接 DVC、MLflow、Zotero。大型第三方框架不能接管项目真源。实现者应为每个依赖记录实际用途、维护入口、固定版本、替代路径及测试责任。

3.2 不以活动量替代科研进度

搜索了多少篇论文、调用了多少工具、修改了多少文件，只能描述活动量。进展应对应某个研究问题发生了什么变化，例如排除一条不满足约束的路线、识别一项证据缺口、完成可复现的对照实验，或形成可审阅的方法说明。

第一版不显示自动估算的“项目完成百分比”。对于事先定义的有限清单，可以显示“已验证3项，仍缺2项”，同时列出清单版本；不能将该比例转写为整个科研项目的完成度。

3.3 全文贯穿的示例项目

示例研究问题是：在车辆位置存在预测误差时，怎样提高移动群智感知任务的完成率。移动群智感知指由参与车辆在行驶过程中采集指定区域的信息。任务分配方法需要估计车辆能否在时限内到达目标区域。

路线A直接使用预测模型输出的到达概率。路线B先校准概率，即检查“预测为80%可到达”的车辆是否实际约有80%到达，再使用修正概率分配任务。路线C简化分配评分，优先检验复杂机制是否真的必要。

某次实验即使发现路线B的概率更准确，也不能据此认定任务完成率提高。前者是预测层指标，后者是系统决策的结果。工作台必须同时呈现已经观察到的变化和尚未检验的连接。这一示例用于定义状态、证据关系和用户交互，不规定产品只能支持该领域。

4 领域对象与探索图谱

4.1 关键术语

  ------------------------------------------------------------------------------------------------------------
  对象                       定义                                         与相邻概念的区别
  -------------------------- -------------------------------------------- ------------------------------------
  Project 项目               研究问题、目标、约束和资料的隔离空间         可包含多个代码仓库和会话

  ResearchUnit 研究单元      围绕一个可说明问题组织的工作范围             可包含多轮对话和多次运行

  Branch 研究分支            从特定基线派生的一条探索路线                 不必对应一个Git分支

  Claim 主张                 可以被证据支持、挑战或暂时无法判断的陈述     模型建议与用户决定都不等于主张成立

  Evidence 证据记录          定位到材料、结果或观测，并说明与主张的关系   论文条目或文件存在本身不是支持证据

  Decision 决策              对候选行动的选择及其理由和授权范围           接受行动不表示科学上已证明

  ArtifactVersion 成果版本   代码、文档、图表或数据产物的不可变版本引用   路径相同不等于内容相同

  ExperimentRun 实验运行     一次具有配置、输入和输出的实际执行           同一方法可以运行多次

  Checkpoint 快照            一组项目修订和成果版本的可恢复清单           不是一句模型生成的总结

  Proposal 候选变更          模型、规则或用户提出的结构化修改             未应用前不改变有效项目状态

  ReadingBrief 阅读说明      为人解释一个对象的背景、结果与边界           与供模型使用的上下文包分开

  ContextBundle 上下文包     提供给一个具体工作回合的约束、知识和来源     不作为用户阅读说明或项目真源
  ------------------------------------------------------------------------------------------------------------

工作回合指一次有明确边界的人机协作，可以包含多个Harness turn和实验run。turn是一次用户输入驱动的模型运行回合，run是一次实际任务或实验执行。研究单元可以跨多个工作回合和会话。第一版通过会话绑定和活动范围表示工作回合，不要求每次对话创建新节点。

4.2 节点粒度

探索图以研究单元为主要节点。建议类型包括文献调研、问题建模、方法设计、实现、实验、综合分析和阶段审阅。一个节点必须能够说明要回答的问题、与当前目标的关系、预期产物，以及何时结束本轮工作。

每条工具调用、每个文件修改或每轮聊天不自动成为节点。它们作为活动保存在节点内部。模型发现主题变化时可以提出新节点，但在归属不明确时应继续显示为“待归类活动”。用户可以合并、拆分、移动节点；这些操作改变组织方式，不删除原始活动。

一个节点可以对应失败或否定结果。实验环境出错属于执行问题；在有效实验条件下观察到反证才可能改变科学主张。两者必须分开记录。

4.3 三种关系分别呈现

探索谱系回答某条路线从什么基线产生。派生关系连接具体修订，组成有向无环图。所谓有向无环图，是箭头有方向，而且不能沿派生箭头回到自身。重新探索旧问题时创建新节点或修订，不在旧历史上加回边。

任务依赖回答某项工作必须等待什么。第一版对生效依赖禁止循环；发现循环应显示冲突并要求调整任务分解。计划依赖不等同于实际发生顺序。

证据关系回答什么支持或挑战了什么。它允许一个证据关联多个主张，也允许同一主张存在支持和反证。证据网络不强制树形，且支持关系不自动传递：A支持B、B支持C，不能直接推导A已证明C。

默认图只突出一种关系。选择节点后可以临时显示关联证据或阻塞关系。无标签箭头不允许承载多种含义。图谱编辑由应用校验语义；画布组件只负责显示和交互。

默认一个图节点代表一个研究单元的当前选定修订。同一单元的修订沿革在历史视图展开，不因摘要或标题变化生成新的探索节点。跨分支共享对象使用引用，不复制成多个事实对象。分支分歧通过分支所选修订和明确关系表达。

4.4 分支操作语义

  -------------------------------------------------------------------------------------------------
  操作                    必须完成的事情                           不允许隐含发生的事情
  ----------------------- ---------------------------------------- --------------------------------
  继续                    在当前范围新建工作回合，记录上下文版本   自动扩张研究目标

  分支                    固定基线、差异假设与继承对象             复制历史中已失效结论为当前真理

  比较                    在明确维度、条件和证据下并列路线         给不明依据的总分或胜率

  从快照继续              创建新分支，保留当时状态及后来反证       覆盖当前目录或删除原路线

  合并                    列出选择继承的结论、方法、文件及冲突     自动合并互相矛盾的科学判断

  暂缓或归档              记录原因、恢复条件和仍可复用的发现       将全部失败探索标记为无价值
  -------------------------------------------------------------------------------------------------

合并研究知识和合并代码是两个动作。知识合并可以成功而代码仍冲突；Git无冲突也不代表方法假设一致。界面必须分别展示结果。

4.5 多维状态

研究单元的工作状态是 planned、active、blocked、paused、finished、archived，分别表示计划中、进行中、被阻塞、暂停、声明的工作范围已结束和归档。finished要求满足该单元的完成条件，或记录明确的停止理由；它不代表科学主张成立，也不能由一个turn或会话结束自动赋值。

主张的评估状态是 unassessed、supported、contradicted、mixed、inconclusive、withdrawn，分别表示未评估、有条件支持、受到反证、证据混合、证据不足以判断和已撤回。supported必须附适用条件和证据，不显示为“绝对正确”。

决策状态是 proposed、accepted、rejected、superseded。用户接受决策表示允许按该选择推进；被替代的决策仍可用于历史查询，但不能作为当前强约束注入。

审阅记录只针对一个具体修订，状态为 unreviewed、needs_changes、accepted。界面将审阅的accepted显示为“审阅通过”，将决策的accepted显示为“采用方案”，不能合并为一个“已确认”。审阅保存目的，例如检查解释是否准确或检查实验配置；通过审阅不自动授权执行，也不表示科学结论成立。对象产生新修订后，旧审阅仍保留，但新修订默认未审阅。用户打开页面不自动等于理解；“需要补背景”或“已理解”只能由用户主动标记，并绑定具体修订，不影响科学主张状态。

4.6 版本与时间

每个对象具有稳定ID与递增修订号。链接尽量定位到具体修订。项目服务保存事件发生时间、系统记录时间和适用时间；三者可能不同。旧笔记今天导入，不能被理解为今天才作出的决定。

历史回看提供两种明确模式：“历史记录回放”按系统记录时间恢复某个检查点已保存的对象；“现在回看”额外显示后来发现的反证和替代决定。导入旧资料后，可以另行按来源时间重建历史，但必须标记为重建视图，时间不明的材料单列，不能声称完整复现当时人的认知。从旧快照开始新的实际工作，默认带上当前已知反证，不能悄悄恢复已经知道不成立的假设。

5 面向人的阅读与审阅规范

5.1 人的说明与模型的上下文分别生成

同一组项目记录产生两个不同产物。ContextBundle面向模型，强调准确约束、有效决策、检索入口和输入预算。ReadingBrief面向人，解释背景、术语、方法、结果、依据和需要判断的事项。两者引用相同对象版本，但不能将同一段高密度压缩摘要直接用于两个目的。

每一份阅读说明都必须能被没有参与原始聊天的领域相邻研究者独立理解。不能以“如前所述”“继续原方案”“上述结果证明”等指代代替实际对象名称和必要背景。背景不足时应显示未记录并提供补录入口；系统可以检索补充材料，但不得虚构当时已达成的共识。

5.2 内容契约

  ------------------------------------------------------------------------------------------------------
  编号                    必备内容                具体规则
  ----------------------- ----------------------- ------------------------------------------------------
  C01                     当前对象                显示项目、研究问题、路线、节点标题、版本和更新时间

  C02                     必要背景                解释对象、原方法和当前矛盾，不能假设读者记得早期对话

  C03                     一项清楚的问题          每个单元明确主要问题；多项独立问题建议拆分

  C04                     方法及变化              先讲作用，再说明机制，最后按需展开符号与代码

  C05                     实际发现                区分工具记录、模型判断、引用结论和用户决定

  C06                     证据与边界              列支持证据、反证、适用条件及尚未证明事项

  C07                     对项目的影响            说明推进、阻塞或改变了哪个问题，不能只列文件变化

  C08                     下一步选择              提供可执行选择、代价和决定理由；没有必要时不要求确认

  C09                     来源直达                从关键陈述进入具体片段、修订或实验运行

  C10                     可修正                  能反馈背景不足、解释难懂、来源错误和结论过度
  ------------------------------------------------------------------------------------------------------

正文一段处理一个主要关系，优先使用明确主语和常用词。复杂名词首次出现给中文含义，随后保持称呼一致。首屏不叠放长缩写链、多个未经定义的符号和多层括号。短句数量或字数只能用于提示密度，不能作为充分理解的机械保证。

必须保留结论强度。“在当前数据和配置下观察到改善”不能为了简洁改成“方法更优”。“代码已运行”不能改成“方法有效”。简化解释必须保留关键前提、限制和缺失证据。

5.3 四层阅读

概览层说明要解决的问题、最近实质变化、当前判断和下一决定。建议控制在一屏的连贯短文内，但允许为必要背景增加内容。关键不确定性保持可见，不放在默认折叠区。

方法层说明输入、输出、核心机制和候选方案的区别。适当使用小流程图或共同维度对比表。先定义比较对象，再说明优劣依据。

实现层展示真实文件变更、公式、参数、算法伪代码和对应关系。对于一个模型声称新增的机制，必须能定位到实现版本；找不到则显示尚未建立对应关系。

证据层展示文献页码、原始对话位置、实验配置、执行结果和原始产物。阅读说明引用同一工作快照中相互兼容的对象版本，并保存文案、方法图、实现与实验之间的映射；这里的兼容不要求各对象的修订号数值相同。后来出现的反证单独展示，不改写原快照。用户可以从深层返回原阅读位置，不因展开内容重新布局整页。

5.4 背景与术语服务

项目保存术语表，记录名称、简明解释、正式定义、适用分支、有效修订和来源。相同符号在不同论文中含义不同，不能自动合并。公式说明应先讲被建模的对象及变量作用，再讲计算关系。

读者偏好只使用用户明确提供的信息，例如“理解系统模型，概率校准需要解释”。不能因职称、打开过页面或多次讨论就推断用户掌握某项知识。用户可以选择“补足背景”“用一个例子解释”“定位实现”“查看变化依据”，这些操作不改变项目科学状态。

模型新增的通用背景必须与项目记录分开标识。外部资料中的一般规律不能未经验证变成该项目的实际实验结论。背景生成失败时仍可阅读原始材料，并显示解释尚未生成。

5.5 阅读说明示例

以下为虚构节点的合格文案，用于实现测试。

当前问题。 本节点研究位置预测不准时，怎样减少把采集任务分给无法到达目标区域的车辆。现有方法直接使用预测模型给出的到达概率，因此模型过于自信时，分配算法也可能作出过于乐观的选择。

本次改变。 路线B在预测与任务分配之间增加概率校准。校准的作用是检查预测概率与实际发生频率是否一致，并修正系统性偏差。任务分配算法仍然使用到达概率，只是输入经过修正。

已经知道的内容。 当前结果文件记录了校准前后的预测误差，支持“校准改善当前样本的概率估计”这一较窄结论。阅读说明同时列出数据版本、计算脚本和运行记录，供用户核实。

仍然不知道的内容。 还没有在相同预算、数据和分配算法下比较最终任务完成率，因此不能认定校准已经改善整个系统。也没有证据说明需要继续增加更复杂的预测网络。

需要的下一步。 先开展保持其余条件不变的对照实验。完成后比较任务完成率及代价，再决定是否将校准纳入主线。用户已经授权该实验时直接实施，不重复请求同一许可。

这个说明能够独立回答研究目的、方法变化和证据边界。正式界面中的“结果文件”“运行记录”必须替换为有名称、版本和定位的实际来源，不能保留空泛引用。

5.6 自动质量检查

规则检查覆盖缺少主体、没有解释的缩写、无法解析的指代、来源缺失、引用版本不一致和状态与措辞冲突。语言规则只用于发现风险，例如长句提醒不能直接判定内容错误。

重要说明再执行语义检查：背景是否足够、结论是否由列出的证据支持、限制条件是否保留、存在的反证是否被遗漏。模型检查器只能提出问题和候选改写。源材料中的真实结果、数值、决定和授权不得由改写步骤自行改变。

每份说明记录输入对象修订、模型与模板版本、生成时间、质量检查结果。任一关键源修订变化后，说明标记为过时并排队更新；在新说明完成前保留旧版，明确其适用版本。不能让后台重写使用户正在审阅的内容突然变化。

6 工作台的信息架构与交互

6.1 项目首页

首页首先显示一段自包含简报：项目研究什么、当前主线是什么、上次访问后发生了什么实质变化、最重要的不确定性是什么。其下依次呈现当前工作、待关注事项和最近成果。完整拓扑图作为相邻视图，用户可以设为自己的默认页。

页面始终可见连接状态、最近成功同步时间及采集范围。没有观察到事件时使用“未知”或“尚未同步”，不使用“没有进展”。后台提炼尚未完成时，活动记录仍可访问。

待关注列表默认突出至多三项高优先级事项，其余可展开。排序依据是影响的目标、被阻塞的工作、证据严重程度和用户设定的时限；不能仅根据模型自报置信度排序。

6.2 探索地图

地图采用二维分层布局。第一层显示研究问题与主要路线，第二层显示研究单元，第三层进入节点内部活动。历史分支可以折叠，当前路径突出显示。相同对象在多个视图出现时引用同一ID，不复制成互不一致的事实。

新增记录不得持续重排整张图。用户可以固定位置、搜索节点、保存视图、恢复上次阅读位置、切换为大纲。跨分支引用使用不同线型和文字标签。颜色同时配合状态名称和图标，不依赖颜色传达含义。

点击节点是浏览动作，不会把正在运行的Harness转到该节点。图上分别标记“正在查看”和“正在执行”。用户明确选择“在此开展工作”后才建立执行绑定，并显示使用的路线、上下文版本和工作目录。

6.3 节点详情

详情默认展示概览，标签页包含方法与实现、依据与结果、历史与版本。固定区域显示本轮问题、工作范围、当前状态、限制和下一步。活动流水折叠，避免每条工具日志争抢注意力。

用户可以提出局部问题，例如“这个模块在整体方法里起什么作用”。回答限定在当前节点与明确关联资料内，附来源；查不到时显示缺失，不用通用解释冒充实际实现。

6.4 路线比较

比较视图以同一研究问题为入口。各路线使用共同维度：解决的具体问题、关键假设、已有支持、反证、未解决事项、实现与实验成本、可解释性及当前决策状态。未知项写未知；没有依据的“创新性高”或“成功率80%”不能出现。

实验指标比较须验证数据、配置、指标定义与聚合方式是否可比。不可比的结果分区展示并说明原因，不能画在同一排名中。不同数据集、预算或随机种子集合下的结果不能仅按数值大小确定优胜方案。

6.5 决策与审阅中心

每项待决定事项说明要选择什么、为什么现在需要选择、可选路线、已有依据、未解决风险、影响对象及建议。支持接受、拒绝、暂缓、要求补充信息；按钮说明将允许的具体行动。

科研决策与工具权限分开。例如“同意检验路线B”是研究范围授权，“允许访问某个目录”是运行权限。工作台必须遵守Harness和操作系统原有权限，不能把研究批准自动转化为无限制文件或网络访问。

用户已经作出清楚的选择或提供持续授权时，系统直接复用其范围。只有出现新范围、关键冲突或缺失必要权限时才再次询问。批量批准必须展示全部影响，不能把隐藏事项捆绑在一个“全部继续”按钮中。

6.6 成果与证据视图

成果视图按具体版本组织代码、方法说明、论文、实验表和图。一次重要变化应回答“改变了什么、为何改变、影响什么、验证了什么、仍欠什么”。语义解释必须关联真实差异；模型声称修改与实际文件不一致时显示冲突。

证据视图可从主张进入来源，也可从一个实验反查它支持哪些主张。默认显示支持和反证两部分。仅有文献元数据时标记“未核验全文”；PDF扫描识别失败、引用定位失效、文件已移动等问题有具体状态。

6.7 可访问性与视觉密度

中文正文初始值为16px、行高1.6，主要阅读栏约38–48个汉字宽；这些是可配置的设计起点，需要通过阅读测试校准。提供缩放与高对比度主题，200%缩放时不丢失关键操作。长公式横向滚动不得阻断整页阅读。关键操作支持键盘，焦点顺序稳定；图谱提供等价的大纲或列表。抽屉打开后可回到原位置；状态变更不自动抢走用户焦点。实现参照WCAG 2.2相关准则，并通过实际键盘和阅读测试验收。[S50]

第一版避免3D图、装饰动画、自动播放历史和难以解释的综合分数。可视化服务于定位、比较和决策。是否易懂用第三方理解任务验证，不能仅依据界面看起来整齐。

7 完整用户流程

7.1 新项目和历史导入

用户选择项目目录及需要导入的会话、笔记、论文和成果。系统先显示识别到的来源、时间范围、文件数量和重复项，再开始索引。未选择的其他项目和会话不进入搜索范围。

导入首先保存原始来源定位和内容指纹，再形成候选研究问题、路线、节点及决定。候选分组与明确记录分开显示。用户只需要确认项目目标、当前路线和关键决定等高价值内容，其余材料可保持未归类状态，不要求在首次使用时整理完所有历史。

导入完成的条件是来源可查、重复导入无重复对象、候选结构可纠正，并生成一份能说明缺失信息的项目简报。不是要求模型构造一段完整且看似合理的项目故事。

7.2 每次开始工作

用户打开项目后阅读变化简报，可以直接恢复上次节点，也可以选择新的问题。系统显示该工作的目标、关联决定、前置依赖和建议收束条件。用户在原Harness中发送消息时，伴随适配器按可用能力提供上下文；用户从工作台启动时，托管适配器建立明确的会话绑定。

工作约定至少包括当前问题、允许范围、预期产物和检查方式。时间、费用或迭代预算由用户可选设置，不强制所有研究任务量化。预算未设置时显示未设置，不能根据任务名称虚构额度。

系统优先继承当前研究单元的有效工作约定。只有目标、范围或关键条件发生实质变化时才展示需要处理的差异；常规恢复不要求用户重新填表或重复批准。用户在普通对话中清楚表达的约定可以形成可核对记录，不要求同时在另一张表单重新输入。

7.3 执行中的持续理解

工作台实时记录可观测事件，按研究单元汇总。主要状态展示当前正在做什么、最近得到什么结果、是否出现阻塞及是否需要用户决定。显示执行事实时不得用模型的自然语言宣称代替工具结果。

模型提出重大方法变化时，系统生成可审阅的候选变更卡。用户可以查看方法差异、受影响主张及实现范围，在现有授权范围内继续，或调整下一步。一般性文件整理和已授权的小修复不需要进入重要决策队列。

7.4 一轮工作结束

事件采集器记录工作回合结束信息；后台生成变化简报和候选知识。应用检查实际产物、来源和状态。只有研究单元声明的完成条件已满足，或明确决定结束该探索时，单元才变为finished；否则保留active，或根据实际情况转为paused、blocked。关联主张仍可能是unassessed或inconclusive。用户需要审阅的对象以具体版本进入队列。

结束时保存下一步建议和未解决问题，使新会话可恢复。未完成摘要不阻止保存原始记录；没有证据的完成宣称不能使验证状态自动通过。

[从原始事件到可审阅修订]

7.5 发现路线不可行

用户或模型发现反证后，系统先定位受影响的假设、决定、实验和成果，生成影响清单。关联对象标记为需要复核，不自动删除，也不立即把所有下游结论判错。

用户可以暂缓原路线，从共同基线新建分支，并选择继承仍有效的资料。系统预览将继承的对象、将保留为历史的对象和需要重新验证的对象。存在代码变化时，默认新建独立工作区；现有目录保持完整。

新会话接收新路线的有效背景，同时附必要的失败经验和后来反证。无需向模型灌入全部错误历史，但也不能让模型再次把已被推翻的条件当成事实。

7.6 跨Harness继续工作

用户选择目标Harness后，系统显示两侧能力差异。新的上下文包包含项目目标、当前节点、有效决定、相关来源和下一动作。迁移的是项目认识与工作范围，不承诺两个模型具有相同内部状态，也不伪装无损迁移整段隐含思考。

目标Harness缺少主动注入接口时，生成可复制的交接材料并显示需要手动传入。未收到会话接受或执行回执时不显示已同步成功。原会话仍在执行时，必须先明确并行还是转移，避免两个执行者无意修改同一工作目录。

8 人类控制与工作节奏

8.1 授权模型

授权以项目、分支、工作单元、操作类别、资源范围及期限定义，可由用户随时撤销。默认允许被选择项目内的读取、整理、候选分析；实际文件或工具执行仍由原Harness权限控制。方法变更、目标变更和对外操作依项目策略判定是否需要新的决定。

模型提出的授权记录不能自我生效。批准来自经过认证的用户操作、可追溯的明确用户消息，或之前有效且覆盖当前范围的授权。模型写下“用户已批准”不构成批准证据。用户消息“可以”只能在目标选择明确、版本和范围可确定时映射到决定，不能批准多个隐藏改变。

已经获准的工作在授权范围内持续执行，不以固定轮数重复确认。用户请求撤销或缩小范围后，新动作必须按新版本授权检查；已经发生的外部副作用单独记录。

导入历史会话、重放旧记录或从旧快照继续，不会重新激活已过期或撤销的授权。历史用户消息可以证明当时的选择；新的实际动作仍按当前有效授权检查。当前已有授权覆盖时继续复用，不因导入或切换视图重复询问。

8.2 四种工作节奏

探索用于获得候选解释和路线；收束用于比较证据并形成选择；实施用于完成已确认的工作范围；复盘用于检查整体方向及未解决问题。这些是可往返的工作标签，不是强制流水线。

系统可以建议切换节奏。例如已有足够材料比较路线时，建议先收束，而不是继续扩大文献搜索。任何建议都应引用已经获得的进展、尚未解决的问题和潜在机会成本。单纯“连续多轮未换主题”只是一条检测信号，不能直接判定低效。

8.3 纠偏检测

第一版优先实现可核实的检测：当前动作与有效约束冲突、准备重复已有失败尝试、论文结论缺少对应证据、重要依赖未解决、摘要引用旧版本、产生新的范围但未说明与目标关系。

每条提醒包含触发依据、关联来源、受影响工作、建议动作以及忽略或暂缓入口。默认合并同类提醒，已处理事项不反复出现。没有新证据时，用户明确选择继续应抑制重复提示；出现新的重大反证可以重新打开事项并说明原因。

“局部过度优化”作为建议类判断，不自动中断工作。系统应先检查是否有新的发现、当前问题价值、用户主动设定的优先级和其他被推迟事项。初期不训练一个无法解释的全局偏航分数。

8.4 干预强度与计算成本分别控制

用户分别配置提醒强度和模型分析预算。低打扰模式不代表减少必要的来源核查；高分析预算也不意味着频繁弹窗。默认采用被动状态和阶段摘要，重要冲突进入待关注列表，只有阻断当前已授权工作的具体问题才即时提醒。

后台分析采用增量批处理：保存原始事件不需模型；短时同一活动合并后再提炼；深度复盘由用户或明确的阶段事件触发。费用上限和并发数可配置，预算耗尽后继续采集与人工管理，暂停额外模型分析并显示原因。

8.5 停止与转向

托管模式下用户请求停止后，状态先显示interrupt_requested，只有收到终态证据才显示interrupted、completed或failed。若无法确认则显示unknown，并保留最后可靠活动。主会话停止不代表子任务、远端实验和已提交作业都已经停止。

转向新节点时，旧运行的迟到事件仍归属旧节点。工作台不得因为用户点击其他节点而重新标记历史。伴随模式没有中断能力时，界面提供回到原客户端的具体操作，并明确请求尚未执行；不能用一条建议消息冒充已经控制了进程。

9 系统架构与技术选择

9.1 组件分工

系统由交互前端、本地应用服务、模型分析任务、Harness适配器和本地数据存储组成。前端不直接改数据库，模型不直接提交有效项目状态。所有有效变更通过应用服务验证对象版本、权限及关系约束。

[本地工作台的组件与权限边界]

前端使用React与TypeScript；本地服务统一使用TypeScript和Node运行时，以减少字段与校验逻辑漂移。数据合同使用JSON Schema，核心HTTP接口使用OpenAPI。图谱采用React Flow，复杂层级布局采用ELK；画布交互和布局不能代替研究关系校验。[S42][S43][S44]

SQLite保存事件、当前投影、索引和任务队列，不引入外部数据库作为第一版前置依赖。FTS5支持基础全文检索；中文术语需要预分词、别名与专门回归测试。选择向量后端前先测量真实失败案例。[S45][S46]

桌面版本使用Tauri封装同一前端和受限本地服务。签名、公证、更新、子进程退出和系统凭证存储分别实施，不能认为加一个桌面壳就完成生产交付。Python作为后续文献解析或科研脚本的可选工作进程，不承担核心权限与状态写入。[S47]

9.3 单一权威状态

SQLite中的项目事件表是有效状态变化的权威历史；对象修订和当前视图是可重建投影。事件和投影在同一事务中提交。原始日志、论文和结果文件使用不可变内容引用保存，不需要把大文件塞进数据库。

Markdown、JSONL、图谱布局文件和面向Harness的状态笔记都是导出或缓存。用户在外部编辑这些文件后，系统将差异作为候选导入，不双向静默同步为第二套真源。导出标记源项目与修订，防止文件监控把自身导出反复重新导入。

SQLite的WAL模式适合本机并发访问，不把活动数据库放在网络共享盘或同步中的云盘目录。跨设备迁移使用关闭写入后的快照或一致性备份，而不是直接同步活跃数据库文件。[S45]

9.4 模型不可用时的行为

浏览、搜索、人工新增或修改、分支、决定、快照和导出必须不依赖模型。自动提炼和解释可以排队，显示未完成、失败原因和重试入口。模型服务的故障不能被解释为科研路线失败，也不能阻止用户访问已有材料。

后台任务绑定固定输入和版本。缓存键至少包含项目、对象修订、来源集合指纹、模型版本、模板版本和读者偏好版本。没有变化的材料不重复提炼；缓存命中不会改变来源证据等级。

10 数据模型与关键不变量

10.1 对象存储

每个可修改实体使用稳定ID、project_id、revision和时间字段。ID不可复用，显示编号与机器ID分开。新修订保存作者、来源及变更原因。第一版可以用对象修订表保存经过Schema验证的JSON，并为检索、关联和状态建立独立索引，避免过早建立大量高度耦合表。

建议持久化集合包括项目、研究单元、分支、图关系GraphEdge、主张、证据、决策、成果版本、实验运行、快照、提案、审阅、会话绑定、能力清单、上下文包、阅读说明、授权与事件。配套domain.schema.json规定字段、枚举、必需项及空值；应用服务补充跨对象约束。

关系必须保存类型、两端对象与修订、产生依据和有效范围。非精确关联另标明“推断关联”或“时间相关”。原始记录没有提供因果关系时，不允许自动生成确定的“因为”。

10.2 来源定位

  --------------------------------------------------------------------------------------------------------
  来源                    最小定位信息                                        核验方式
  ----------------------- --------------------------------------------------- ----------------------------
  会话消息                Harness、会话ID、消息ID或明确范围、角色、内容指纹   打开原始消息并高亮片段

  文献                    稳定文献标识、版本、页码或章节、片段定位            显示原文与所支持陈述

  代码                    仓库、提交或内容指纹、文件、符号或行范围            查看固定版本及差异

  实验                    run ID、配置、数据版本、脚本版本、结果位置          查看一次实际运行的输入输出

  用户决定                认证动作或明确用户消息、对象修订、选择和范围        检查当时作出何种选择

  重建解释                所用来源集合、生成时间、模型、标记                  显示为事后解释而非历史事实
  --------------------------------------------------------------------------------------------------------

原始文件不存在时记录缺失，不制造一个不可验证的新引用。网址和文件路径不是内容版本；重要外部材料可在授权范围内保存片段与指纹。大型数据只保存清单和引用时，必须显示可用性。

10.3 证据评价

主张必须明确适用对象、条件、时间和比较基线。证据关系分别记录支持、挑战或背景关联，以及依据的具体片段。信息抽取的模型置信度只反映提取不确定性，不能显示成科学结论成立概率。

合同中的attach_evidence.reference表示背景引用，映射到uses关系或阅读说明的背景引用，不生成supports边。图中的支持或反证边固定两端修订；相关主张或证据改变时标记需要重新核验。探索谱系边保留当时的版本关系，不随当前标题或摘要更新而改写历史。

同一论文的摘要、转述和二次总结不能被统计为三项独立支持。来源去重与派生关系用于提示同源证据。用户选择一条路线也不能改变证据强度。缺少评估时保持unassessed；相互冲突但暂无法解释时使用mixed并列出冲突条件。

代码测试通过只支持被测试的实现性质。一个实验成功退出只支持执行完成。系统可以提出主张状态变化，但必须记录评价方法、范围和批准或授权依据，不根据日志中的“success”自动升级研究结论。

10.4 并发与幂等

入口采用至少一次接收和幂等落库，不承诺跨Harness全局只投递一次。幂等标识优先由来源实例、会话和源事件ID构成。相同ID与相同内容重复到达只保存一份；相同ID却有不同内容指纹时进入冲突记录，禁止静默覆盖。

应用分配递增event_seq，表示系统接受或应用顺序，不冒充真实发生时间。保存occurred_at和recorded_at，来源可有自己的序号。迟到结果可以先保存不完整记录，等待前序补齐；没有证据时不伪造开始时间。

变更请求的expected_revision统一指项目修订。需要检查具体提案或对象时另传expected_target_revision。应用在事务内比较版本，冲突返回409与当前修订。后台旧结果只能作为待重检候选，不得覆盖用户刚刚作出的新决定。

原始采集中的版本仅用于关联当时的上下文，不能因项目已经前进而丢弃真实观测。派生说明中的版本表示固定输入快照；保存旧输入的分析结果可以成功，但只能显示为对应旧版的材料。只有试图改变有效业务状态时，才执行相应的并发与当前授权检查。

10.5 权限与身份

actor身份由服务端根据调用凭证和来源确定。模型请求体不能指定自己是用户，不能提交已批准状态。可信来源适配器也只可以报告其实际观察到的用户消息，不能让任意文档文本变成用户授权。

原始资料是数据，不能执行其包含的指令。文件内容声称“关闭审阅并批准全部修改”时，只能作为文本记录。MCP令牌仅允许规定的读取和候选提交，人工批准使用独立身份通道。

这些是应用层边界。同一操作系统用户下拥有完全文件权限的其他进程仍可能直接修改文件；需要更强隔离时使用操作系统权限或沙箱，不能宣称一个本地API已经阻止所有绕过路径。

10.6 必须始终成立的规则

1.  模型输出和导入材料不能自行成为有效用户批准。
2.  有效主线决定只能由授权操作或有效既有授权变更。
3.  已接受的决定不自动成为已验证的科学主张。
4.  对象新修订不会自动继承旧修订的人工审阅。
5.  被替代或撤回的知识不作为当前约束注入；历史查询可以返回但必须标记。
6.  不同项目和未经授权的分支资料不混入上下文。
7.  重要陈述至少能定位到来源，或明确标记缺少来源。
8.  图节点合并、拆分、移动不删除原始活动和产物。
9.  从历史快照继续默认创建新分支，不覆盖现有目录。
10. 事件与有效投影原子提交，界面只发布已提交版本。
11. 视图选择与执行绑定分离，迟到事件保留原归属。
12. 未得到终态回执时不把停止、恢复或同步标为成功。

11 记忆与上下文处理

11.1 保存层次

项目记忆分为目标与约束、有效决定、知识与证据、当前状态、原始经历五类。目标与硬约束体积小、频率低；知识和经历可持续增长。不同层次使用不同有效期和加载策略，不采用一个不断追加的全量摘要。

目标可以由研究者调整，系统保留修订和理由。主张可以因新证据被挑战。旧的模型建议不因时间久或频繁出现而变成事实；有效约束也不因长期未提及就自动衰减删除。

11.2 增量提炼流水线

采集首先保存来源；确定性标准化补充会话、文件和时间信息；语义分析提出归类、主张、决定或问题；验证器检查字段、来源和当前版本；策略决定自动应用低影响结构更新还是保留候选；最后更新视图和解释。

低影响自动应用只包括已明确绑定的活动归档、可核实运行状态、来源索引等。涉及研究目标、科学评估、有效决定、重要成果状态或关键依赖的修改必须经过相应授权。自动归类可以更正；无法判断的资料保留待处理，不强制填满所有字段。

提炼器输出必须符合Schema，不允许自由文本直接写数据库。结构错误可以进行一次受限修复；仍失败时保留原始输出为诊断材料，标记任务失败并等待重试，不无限递归调用模型。

11.3 检索顺序

检索先确定项目、当前分支、有效修订、时间模式和用户权限，再执行关键词、术语别名和可选语义搜索。随后按明确关系扩展到前置决定、支持与反证、被替代记录和相关失败经验，最后选择带来源的必要片段。

语义相似度不能覆盖硬约束或分支隔离。用户问当前方案时，已失效记录只能作为历史解释附带返回。用户问为何放弃旧方案时，必须同时返回当时理由和后续替代状态。检索为空时明确没有足够记录，不从一般知识编造项目历史。

中文测试集必须包含两个字的术语、中英混用、缩写、同名方法、数学符号、否定表达和相近但不同的研究问题。短词检索不能只依赖三字切分。先完成词法与结构关系基线，向量检索是否加入由错误分析决定。

11.4 上下文包结构

ContextBundle包含项目问题与约束、当前工作约定、有效决策、必要背景、相关证据、失败尝试与反证、未解决问题、允许动作及来源索引。每个条目记录对象与修订、来源和被选入的原因，便于排查为何模型遗漏或误用信息。

默认设置可配置的token预算。预算先为用户明确目标与硬约束保留，再分配当前任务和相关证据。重要背景超出预算时生成带警示的缩略版本并保留精确来源；不得无声丢弃不可违反的约束。token估算不准确时使用保守余量并显示估计性质。

上下文在会话开始、工作切换、重要决定变化和压缩后按能力更新，不在每一条普通消息重复注入完整项目。包的ID和版本写入SessionBinding。工作台应区分已构建、已发送、已被接口接受；无法证明模型实际遵循时不能显示“已经理解”。

11.5 纠错与污染恢复

用户标记一项记忆错误时，记录纠正及适用范围，更新相关投影，并使受影响的阅读说明与上下文包过时。已发送的上下文不能被假装撤回；下一可用注入点提供纠正，必要时建议新会话。

删除私密来源应同时清理搜索索引、向量缓存、导出缓存和派生说明中的可恢复内容。可以保留不含敏感正文的删除审计。外部模型已接收的内容不能承诺远程撤回；产品应让用户在发送前知道数据去向。

12 Harness集成规范

12.1 三种连接模式

  ----------------------------------------------------------------------------------------------------------------------------------------
  模式              用户如何工作                 工作台负责什么                                   不应承诺什么
  ----------------- ---------------------------- ------------------------------------------------ ----------------------------------------
  档案模式          导入选定历史与成果           索引、重建、检索、人工整理                       不能控制原会话

  伴随模式          继续使用原Harness客户端      Hooks或正式事件采集、MCP查询、按能力提供上下文   不能假设接管任意活跃桌面会话

  托管模式          工作台通过正式协议启动会话   明确绑定、事件、输入、中断与接口允许的审批       不绕过原权限，也不保证外部副作用可回滚
  ----------------------------------------------------------------------------------------------------------------------------------------

同一项目可以混合三种模式。一条活跃会话只由一个控制器负责写入，旁路观察可以多路但必须去重。用户自行在外部客户端改变状态时，以实际新事件更新，不覆盖为工作台旧计划。

12.2 已核验的官方接口基础

Codex官方app-server提供线程启动、恢复和分叉，以及工作回合启动、转向、中断和事件通知，可用于工作台自己创建或正式管理的会话。Hooks提供生命周期扩展，但部分托管工具不经过本地工具Hook；transcript路径的文件格式也不是稳定接口。[S33][S34]

Claude Agent SDK提供会话及消息读取、运行交互和权限回调等接口；Hooks提供用户消息与工具活动等事件。官方文件checkpoint只覆盖部分编辑路径，不等同于完整项目快照。双方同名Hook的字段和可阻断能力可能不同，不能共用一份未经适配的实现。[S35][S36][S37]

上述是官方文档层面的能力基础，不是用户机器的兼容保证。任何发行版都必须列出实际测试的Harness名称、CLI或桌面表面、版本范围、连接模式、认证路径和通过的测试。无法核验的能力标为unverified。

12.3 能力清单

每个适配器连接时执行probe，分别报告历史读取、消息观察、工具观察、启动时注入、用户消息前注入、压缩后注入、新建、恢复、分叉、转向、中断、工具审批及文件快照能力。每项使用supported、partial、unsupported、unverified之一，并附版本和限制。

能力必须按实际连接对象判定，不能仅按品牌名。某项仅在SDK托管模式可用时，原桌面伴随连接应显示不可用。界面据此启用动作；无法支持的控制请求返回明确错误，不通过提示词假装实现。

12.4 关键差异与设计后果

  --------------------------------------------------------------------------------------------
  情况                                方案要求
  ----------------------------------- --------------------------------------------------------
  Codex本地Hook不覆盖某类托管工具     记录采集缺口，必要时使用正式事件流补充，不宣称全量记录

  同名压缩Hook控制能力不同            由各适配器生成准确输出，不共享阻断语义

  历史格式随版本变化                  优先正式读取API，私有文件解析器有版本检测与失败降级

  已有会话不能被工作台接管            保持伴随模式，提供可理解的手动操作或新托管会话

  Harness升级后能力不明               禁用未知控制操作，仍允许安全的历史浏览与导出

  认证失败或额度不足                  显示具体失败，保留工作状态，不自行替换身份或扩大权限
  --------------------------------------------------------------------------------------------

适配器安装必须备份并合并用户配置，允许卸载恢复，不能覆盖现有Hook、Skill或MCP设置。需用户信任的脚本按宿主流程处理。不得为减少安装步骤开启bypass或无限权限。

12.5 会话绑定与双向控制

SessionBinding固定project、branch、unit、context_bundle、worktree和base_project_revision。具体工作回合使用对应的turn标识或消息范围。用户在地图中切换浏览不会修改绑定。一个会话跨节点工作时按回合边界追加绑定记录，不整体重归类历史。

转向命令先记录意图，再按适配器能力中断或安排下一回合。旧回合的消息仍关联旧绑定。若需要新的干净上下文，使用新会话并明确携带的背景；不要默认直接分叉全部旧聊天就能隔离错误假设。

12.6 MCP工具边界

MCP是向智能体提供工具和资料的协议入口，不是一个能够强制模型按计划工作的控制器。第一版只开放获取当前背景、历史检索、读取节点与阅读说明、提交候选变更。人工批准、授权提升、强制恢复和直接改写事件真源不开放给模型凭证。[S48][S49]

工具返回带来源和范围的结构化数据，并限制条数与大小。检索到的文献、网页和历史聊天作为不可信资料处理，不能更改应用政策。工具名和Schema由版本化合同发布，后续新增能力必须保持权限边界。

13 文件版本与实验复现

13.1 研究分支与文件工作区

纯调研分支可以只有知识和决策差异。需要并行修改代码时使用Git worktree等独立工作区；Git负责文件版本，研究图负责方法意图和证据。[S38]

快照记录Git提交、未提交差异、选定未跟踪文件、关键文档指纹和保存范围。只保存commit而忽略未提交文件不能显示为完整快照。大型数据和模型使用内容寻址清单，用户明确选择是否复制实体文件。

13.2 快照与恢复流程

建立快照时固定项目修订与对象集合，采集文件状态并验证内容指纹，最后提交快照清单。任何步骤不完整都显示部分可恢复，并列出缺项。恢复前检查原始对象可用性、目标目录、未提交修改、磁盘空间及环境约束。

采集还必须检查跨文件一致性。托管模式在能力允许时协调已知写入者暂停，确认静止后保存；伴随模式不能假定控制了外部程序，应比较采集前后的工作树、文件清单与内容指纹。变化时重试或标记部分快照；无法证明来自同一逻辑版本时，不得仅因每个文件都计算了hash就显示完整快照。

恢复默认新建分支和目录，不运行破坏性重置。完成后逐项核对内容指纹，报告认知状态、代码、配置和数据各自恢复情况。某项实验数据仍在断开的远端时，应说明认知状态可恢复而实验暂不能复现。

13.3 一次实验的最小记录

实验运行至少保存关联主张与节点、待检验问题、输入数据版本及划分、代码与环境版本、配置与随机种子、执行命令、开始结束状态、输出清单、指标定义与计算方式。缺失字段可以为空但必须暴露，不由模型猜测。

实验结果附比较条件、基线、重复运行与统计汇总信息。是否需要多随机种子、置信区间或显著性检验取决于方法和实验方案；系统不机械要求每项工作使用相同统计流程，但必须显示采用的依据和缺失条件。

DVC可以管理实验变体、数据与结果，MLflow可以记录运行参数、代码版本、指标和产物。适配器将外部run映射为本系统ExperimentRun；科学主张与支持关系仍由工作台管理，不依据外部run显示成功就采纳结论。[S39][S40]

13.4 远端实验和断联

远端实验有独立run ID、调度标识、心跳和最后可信事件。连接断开表示状态未知，不等于执行失败。请求取消后等待调度系统或进程终态；中断一个本地聊天不能推断远端作业停止。

第一版可以导入远端结果清单而不内建完整集群调度。原生SSH、Slurm或其他调度适配器放在扩展阶段；启用前必须通过断连、重复提交、取消回执和产物去重测试。

13.5 文献管理

支持用户选择PDF、文献元数据和笔记导入。Zotero可通过官方API只读获取选定资料，不直接修改其内部数据库。[S41] 证据引用必须定位到内容及版本；论文标题、作者和摘要可帮助检索，但不能自动等同全文支持。

解析质量不足时保留原始PDF和人工定位入口。图表和公式识别不可靠的部分必须标明。对不同论文中的同名变量或相似方法，术语服务保留局部定义，避免跨文献合并含义。

14 实施合同与核心接口

14.1 合同的交付范围

配套目录contracts包含五个文件：domain.schema.json规定领域对象及字段约束；core-api.yaml规定HTTP操作和权限；example-project.json提供可加载的虚构项目实体快照，事件数组明确为节选，不能用来重放完整历史；acceptance-cases.json提供带前提、操作和预期结果的验收场景；README.txt解释跨文件不变量和验证范围。这些文件是实现输入，不是已经运行的系统。

合同使用JSON Schema 2020-12和OpenAPI 3.1。实现者必须由同一合同生成或校验前后端类型，不能各自维护含义不同的同名字段。前端表单校验用于及时提示，服务端校验才决定能否提交。数据库迁移版本、API版本、导出及事件信封的schema_version与模型提示模板版本分别管理；单个实体的revision表示其内容修订。

稳定对象ID使用对象类型前缀和随机唯一标识，例如prj_代表项目、unt_代表研究单元。示例中的可读短ID只用于夹具。ID不能携带用户姓名、绝对文件路径或秘密。对象重命名不改变ID；大文件内容以摘要定位，文件路径只是可变位置。

  --------------------------------------------------------------------------------------------------------------------------------------------------------------

领域内容修改使用类型明确的命令封装成Proposal。命令包含目标、具体变更与理由；Proposal.target_revision_refs集中保存目标及依赖对象的版本，应用时另以expected_target_revision检查提案自身版本。不允许接收任意SQL、任意JSON路径修改或任意Shell字符串来绕过业务规则。批次中的命令全部通过检查后一次提交；任一失败则整个业务批次不生效。

核心合同固定项目状态、资料登记和权限闭环。可视布局、PDF预览和更多格式解析等辅助接口可以按模块增加，但必须在实现前补齐请求结构、范围限制和错误行为。辅助接口不能成为另一条不经过版本与授权校验的写入路径。

14.3 两类版本与事件序号

Project.revision用于有效项目语义状态的并发控制，例如修改目标、采纳路线、变更主张评估或建立有效授权。event_seq用于全部已保存事件的顺序。只收到原始日志、保存候选提案或生成一份派生说明时，不应仅因该后台动作让用户正在审阅的项目版本失效。事件可以连续增加而project_revision_after保持不变。

每个对象仍有自己的revision。Proposal保存提出时的base_project_revision以及它实际依赖的target_revision_refs；ReadingBrief和ContextBundle保存精确的输入对象修订。应用提案时检查当前请求的expected_revision、提案本身版本及关键目标版本，不能因“基础项目修订不同”一概把无关变化当成冲突，也不能忽略真正改变了前提的变化。

领域事务确定哪些变化影响项目语义修订，并在合同测试中固定规则。新建一个候选提案不能自动使该提案自己过时。审阅期间追加一条无关工具日志，也不能让用户反复刷新并再次确认。目标、证据或方案发生实质变化时，则必须显示差异并要求按新版本判断。

14.4 有效变更的提交顺序

服务接收命令后，依次完成鉴权与项目范围检查、幂等检查、输入Schema检查、项目和目标版本检查、状态转换检查、图关系检查、授权范围检查，再生成新对象修订。在同一事务中保存完整事件、对象投影及后续后台任务，提交成功后才发送实时通知。

与外部工具交互使用事务外执行、事务内记录的方式。例如启动Harness时先保存待启动请求，再调用接口，收到回执后保存绑定及状态。数据库事务不能长时间等待模型或外部进程。崩溃后根据请求ID与可查询的外部状态恢复；无法核实是否已经执行的动作进入unknown，不盲目重放可能产生副作用的命令。

用户已有范围授权时，可信策略服务可以在检查该授权后应用相应变更，并记录所用Grant。模型接口仍只有提交候选的能力，不能获取或调用内部应用身份。自然语言授权的解析结果先绑定可核实的真实用户消息和具体对象，模糊的“继续”不能被扩张为新的研究目标。

14.5 错误与用户呈现

  -------------------------------------------------------------------------------------------------------------------------
  情况                                     接口结果                用户看见的处理方式
  ---------------------------------------- ----------------------- --------------------------------------------------------
  输入结构不合法或含越权身份字段           400                     标明无效字段，保留可修正输入

  登录或本地会话身份失效                   401                     保存未提交输入，重新建立本地用户会话

  已识别身份但没有操作范围                 403                     说明缺少哪类范围及已有授权为何不覆盖

  对象不存在或不在可见项目                 404                     不泄露其他项目对象是否存在

  项目、目标、幂等内容或活动执行占用冲突   409                     展示相关差异或正在执行的绑定，允许重建候选，不静默覆盖

错误响应至少带错误代码、可读说明、关联请求ID和可恢复建议，避免把堆栈直接显示给科研用户。开发详情在单独区域查看。界面不能在请求发送时就乐观显示“已停止”“已授权”或“恢复成功”；需要与真实回执对应。

14.6 状态转换约束

研究单元可以从planned进入active；active可转blocked、paused或finished；阻塞解除和暂停恢复后回active。结束后重新开展工作必须有新修订及理由，或创建明确后继单元。archived用于隐藏日常工作而保留历史，恢复时记录恢复理由。任何状态变化都不能删除审阅和来源。

主张状态变化由具体证据和评价产生，没有固定的“向上进度条”。supported可以变为mixed或contradicted；撤回后新主张应说明与旧主张的关系。Decision由proposed变为accepted或rejected；替换已采纳决定时创建新的决定，并将旧决定标为superseded，保留当时理由。

Proposal在candidate时尚待检查，ready表示结构和来源检查已满足应用条件，不表示已被人接受。applied必须关联实际应用事件；rejected保留原因；stale说明依赖前提改变，需要重建或明确重新核对。前端不得仅凭模型文本显示ready或applied。

执行状态单独遵循宿主事件。请求中断后的迟到完成回执可以使最终状态成为completed，因为任务可能已经完成；此时不能为了符合用户请求而伪报interrupted。子任务和实验运行分别维护状态，主会话终态不自动向下传播。

15 可靠性、数据保护与维护

15.1 本地进程与访问边界

本地服务默认只监听回环地址，使用随机会话凭证，校验Host与Origin，写入使用CSRF保护。浏览器页面、MCP客户端、后台适配器和模型任务使用不同权限身份。第一版不提供开放局域网访问开关；以后新增远程访问需要独立认证、传输加密和权限设计。

连接凭证保存于操作系统凭证存储或用户明确配置的受限位置，不写入项目内容、导出快照、提示词日志和错误报告。诊断包默认去除凭证、完整对话和私人路径，并显示发送清单。遥测默认关闭；启用时说明字段与目的，不能将研究正文隐藏在遥测事件中。

资料中的代码片段、文献建议和模型输出默认只供阅读。执行实验命令必须来自用户确认的工作配置和受约束执行器，不能直接把文献中的字符串传给Shell。文件访问限制在项目授权根目录及明确加入的外部资料，处理路径穿越、符号链接和不受信任压缩包。

15.2 内容保存与删除

原始来源先落入临时位置，完成指纹计算和格式检查后以不可变内容保存，再在事务中建立引用。中途崩溃留下的孤立临时文件可回收，不能留下引用了尚未落盘内容的“完整证据”。同内容去重不删除其不同来源关系。

普通纠错通过新事件保留历史；涉及隐私删除时执行明确的数据清除流程。删除记录所含正文、原文副本、搜索片段、派生缓存和备份范围必须分别说明。不可变历史并不意味着永远保留敏感正文：清除范围必须包括Event.payload.after_entities等历史事件中的正文，而不只是当前投影与附件。

实现可以使用可清除的事件内容引用，或在受控清除事务中脱敏历史载荷并保存不含敏感内容的删除审计。选择字段级加密时必须销毁对应密钥并核实副本范围。清除后，事件重放生成带删除标记的状态，不再承诺完整重建被清除内容。受应用管理的备份同步处理；已由用户另行复制或导出的副本列为需要外部处理的范围，不能宣称已经从所有位置消失。

备份默认保持本地，用户可选择可信目的地。保留策略、备份频率和磁盘配额可配置。达到配额先暂停非必要模型缓存与大附件复制，显示影响，不悄悄删除唯一证据或已确认决定。

15.3 故障恢复

服务启动时检查数据库迁移版本、未完成任务、内容引用和适配器连接状态。后台任务采用持久队列，每项绑定输入修订、重试次数及幂等键。只读分析任务可重试；有外部副作用的任务先核实外部状态再决定是否重试。

未被隐私清除的事件和投影必须能在测试库中完整重放，得到相同的领域状态；已清除内容按删除标记重放。不能只保存一句“更新了决定”的摘要作为事件；应保存足够的对象新修订和引用。索引损坏时可以重建，重建期间允许浏览对象与历史，但提示搜索暂不完整。

升级前建立一致性备份并进行Schema兼容检查。迁移失败停止写入，提供恢复上个兼容版本的明确方法；不能让旧版程序直接打开已经不兼容的新数据库继续写。导出包包含版本清单与内容摘要，恢复后核对对象数量、引用完整性和必要文件可用性。

  操作                     初始目标                测试条件
  ------------------------ ----------------------- --------------------------------------
  已索引首页及节点读取     p95不高于1秒            本机温缓存，不含模型生成和外部网络

15.5 依赖与兼容管理

仓库提交锁文件，固定核心依赖的已验证版本，持续维护软件物料与许可证清单。图组件、布局引擎、数据库驱动、文档解析器和Harness适配器分别测试。正式发布不能依赖一项只在某个未固定alpha版本中存在且未经验证的控制能力。

Harness更新后重新运行能力探测与契约测试。适配器声明的可用范围和实际测试版本一同展示。外部项目的许可、维护地址和功能变化须重新核验，不能依据本方案对未来版本自动作出许可或兼容承诺。

16 验证方案与验收标准

16.1 分开验证四类结果

第一类是软件正确性：状态、权限、版本与恢复是否可靠。第二类是信息正确性：能否找回有效知识、识别反证和保留未知。第三类是人的理解：用户是否能解释方法、定位证据及判断下一步。第四类是长期工作结果：是否减少无意重复探索、延后发现错误和不必要管理负担。任何单项通过都不能替代其他三项。

自动测试覆盖可确定规则，人工任务评估理解与决策。不能用另一个模型给出的“清晰度9分”替代真实用户任务，也不能用高满意度证明科研结论正确。

16.2 必须通过的工程场景

配套acceptance-cases.json提供逐项用例。至少覆盖以下类别，任一关键不变量失败均阻止稳定版发布。

  ---------------------------------------------------------------------------------------------------------------
  类别                                必须验证的行为
  ----------------------------------- ---------------------------------------------------------------------------
  权限                                模型不能批准自身建议；伪造actor无效；有效既有授权可复用；撤销后阻止新动作

  并发                                用户新决定不会被旧摘要覆盖；版本冲突不部分提交；重复事件不产生重复节点

  来源                                推断关联不能显示精确因果；同源重复不增加独立证据数；引用失效可见

  图与分支                            禁止派生与生效依赖循环；从旧快照继续保留后续反证；知识合并显式处理冲突

  状态                                实验退出成功不改变主张真值；打开页面不等于理解；新修订不继承旧审阅

  会话                                点击地图不改变执行绑定；迟到事件归旧节点；中断请求与终态分开

  故障                                崩溃可恢复；断连显示未知；SSE重连去重；索引可重建；迁移失败可回退

  数据                                跨项目检索隔离；敏感内容删除清理派生缓存；无模型仍可读取、编辑与导出

  阅读                                陌生读者能找到背景、定义、方法、依据和局限；图谱有等价大纲
  ---------------------------------------------------------------------------------------------------------------

测试应使用真实边界而不是只复制实现逻辑。例如模拟“停止请求发出后任务先完成”和“用户批准前后台新证据到达”，核对最终状态与说明。软件稳定性测试使用故障注入、重复投递和乱序事件，不依赖模型每次生成相同文本。

16.3 记忆与证据评测集

使用得到许可的真实项目材料构造时间切分评测集，并辅以人工设计的困难案例。先规定某一时间截点可见哪些来源，再提出查询；未来证据不得泄露给要求重建当时记录的测试。当前有效查询则必须包含后来纠正和替代决定。

查询覆盖：当前目标、旧选择原因、已否定路线、主张适用范围、跨会话线索、来源定位、没有答案的问题、中英文混合术语、同名不同方法、历史导入和证据冲突。标准答案由研究负责人核对，并记录可接受证据集合，而不是只比较一段标准措辞。

主要指标包括有效证据召回率、来源定位正确率、过时知识误用率、无依据确定回答比例、跨项目泄漏数量、延迟与每次有效答案成本。用户批准检索到的答案不反向修改标准答案。在预先定义的隔离与攻击测试集中，观察到的跨项目泄漏和未经来源支持的授权推断必须为零，并报告测试规模与覆盖。有限测试不能证明所有真实环境永不出错；项目范围过滤和授权校验还须独立通过确定性工程测试。其他指标与基线比较，报告误差和失败类型。

先比较普通关键词检索与结构化检索，再评估是否增加向量或专用记忆服务。每次只改变一个重要组件，保持语料、问题、模型和预算一致。公开长期记忆基准用于补充，真实科研问答才是本产品的关键适配测试。[S01][S02]

16.4 人的理解测试

邀请没有参与原始聊天、但具备相邻专业背景的读者。比较原Harness总结、结构化但未补背景版本，以及本系统阅读说明。同一研究节点的不同版本分配给不同读者组；同一读者跨条件时使用难度匹配的不同节点，并平衡顺序。不能让读者先学到某节点的答案，再把该节点另一版本的表现当成独立观察。

读者必须能用自己的话回答：研究对象是什么；为什么开展本项工作；方法改变了什么；证据支持到哪一步；尚未证明什么；下一步需要选择什么。再要求定位实现版本和一条原始证据。评分标准在测试前确定，评价内容准确性而不是复述术语数量。

初始可用性门槛建议为：不少于80%的有效“读者×节点任务”中，读者无需研究者口头补充即可正确回答上述六个问题中的至少五个。“把未验证主张误读为已成立”单独记为关键错误，不能被其他问题答对抵消；指定发布测试集内不接受此类关键错误。至少一位领域评审复核标准答案和评分。该门槛是待验证的产品标准，不是已有研究结论，也不表示所有未来读者都不会误解。

阶段A开始前冻结首轮测试计划：读者人数、节点数量、条件分配、退出与无效样本规则、关键错误定义和评分方式。形成性测试建议至少覆盖8名不同知识背景的读者、6个具有方法与证据差异的节点；该规模用于发现可用性问题，不作为证明长期效果的统计保证。发现同类背景缺失或误导时修订内容契约，不能仅调整字号掩盖问题。

同时测量定位时间、反复跳转次数、需要补背景次数、误解类型和解释阅读负担。可选自评“理解了”只作为辅助信息，不强制用户每轮答题，也不把理解测试作为日常使用的门槛。

16.5 控制权与长期使用评估

通过注入可识别的问题评估控制能力，例如悄然改变比较条件、重复已失败方法、把环境错误当成理论反证、忽略后来证据、把代码成功运行当成效果提升。记录用户能否发现、发现所需时间、干预是否执行到位，以及误提醒造成的干扰。

基线至少包括原Harness加聊天历史、文件化项目笔记、历史检索加摘要、本系统完整体验。先用同材料的任务测试排除显著缺陷，再在真实项目中进行多周试用；数月价值须通过更长观察确认，不能从一次演示推出。

长期指标建议包括恢复项目背景时间、可避免的重复探索、错误在后续检查前被发现的比例、范围变化被明确记录的比例、纠正系统记录所需操作，以及每周管理负担。记录任务复杂度、使用经验和项目阶段等混杂因素；首轮试用用于改进设计，不声称严格因果。

系统不优化“让用户更信任AI”这个单独目标。更合理的结果是：正确内容可以迅速核实，缺乏依据的内容容易被识别，人能够及时改变方向，并且管理工具本身没有占据过多工作时间。

17 实施顺序与交付管理

17.1 第一版与扩展版边界

首个稳定版本包括本地单用户多项目、历史导入、手工修正、研究单元与三类关系、主张与证据、决定与授权、四层阅读、项目背景恢复、分支比较、默认非破坏性快照继续、基础检索和可读导出。至少一个Harness的托管闭环必须通过真实测试，另一个Harness至少通过档案和伴随闭环，并明确其控制能力。

托管模式是可选入口，用户可以继续在原Harness中正常对话。伴随模式验收采集、背景恢复和能力透明，不要求原接口不存在的中断能力。不能为完成验收强制所有日常工作迁移到工作台内。

若发行说明宣传同时完整支持Codex与Claude Code，则二者都必须完成所宣传连接模式的真实测试；不能把其中一个仅有设计的适配器列为已支持。产品核心不能依赖特定模型品牌，连接器失败不影响已有项目。

桌面签名发布、多操作系统安装器、团队实时协作、原生集群调度、复杂自动规划、全项目向量数据库、自动论文写作和3D图不属于首个稳定版的必备条件。这些功能按实际用户瓶颈逐项加入，不以功能数量决定项目进度。

17.2 分阶段可交付结果

  -------------------------------------------------------------------------------------------------------------------------------------------
  阶段                          实现内容                                                 通过条件
  ----------------------------- -------------------------------------------------------- ----------------------------------------------------
  阶段A：可理解样机             固定示例、首页、节点阅读、图与大纲、比较、审阅语义       陌生读者理解任务通过；不接真实模型也能解释完整闭环

  阶段B：可靠本地核心           Schema、事务、版本、授权、手工编辑、事件重放、备份       核心不变量、重复投递、并发和故障恢复测试通过

  阶段D：长期记忆与纠偏         历史导入、检索、增量提炼、过时检测、失败经验、阅读更新   真实语料错误分析与提醒负担达到预定门槛

  阶段E：第二连接器与科研资料   第二Harness、文献定位、实验导入、跨Harness交接           能力矩阵准确；迁移不丢关键约束和来源

阶段A与B可以部分并行，但阅读体验不能等全部后端完成后再处理。每阶段保留可运行且可审阅的版本；不能用大量没有界面的基础设施代替用户闭环。时间和人力估算须在完成样机与一个真实连接器后按实测工作量制定，本方案不提供没有依据的工期保证。

进入阶段D前，团队根据前期基线固定记忆正确性、旧知识误用、延迟和提醒负担的具体门槛，并保存测试集版本。不能在看到候选系统结果后再修改门槛以宣布通过；确需调整时说明原因，并同时报告旧标准下的结果。

17.4 交给开发者或AI的工作规则

每项实现任务必须写明要改善的用户行为、所属需求编号、涉及合同、允许修改的模块、输入样例、完成条件及验证方式。先实现能独立审阅的小闭环，例如“用户接受一个有来源的路线决定并看到修订”，再连接下一段，不将整份方案一次交给编码助手自由扩写。

实现者遇到未知能力时，先查正式文档并做最小连接实验。接口实测失败则在能力矩阵标记，不得通过虚构事件或硬编码成功状态通过演示。缺失产品决定形成有选项和影响的设计提案；已有规则清楚的普通实现细节由实施者自主处理，不反复要求产品负责人批准。

每次交付同时提供：可运行版本；用户能看到的行为变化；合同和迁移差异；通过的测试与未覆盖项；实际限制；从干净环境启动和回退的方法。代码量、工具调用量和模型自述完成情况不作为验收依据。

开发用AI也必须遵守同样的语义：报告实际改了哪些模块、为何改、怎样验证，以及仍有什么不确定。不要生成一篇密集架构总结替代可运行结果和清楚解释。重要设计决定写入版本化决定记录，保留候选、依据与被替代关系。

17.5 稳定版完成定义

稳定版发布前必须能够完成一个从历史导入开始、经过理解背景、执行工作、审阅证据、发现反证、建立新分支、跨会话继续的真实演练。演练中用户可以停止或调整执行，所有关键状态都有来源，缺失能力明确可见。

还必须完成一次从备份恢复项目、一次模型完全不可用时的人工工作、一次Harness升级或接口失败的安全降级，以及一次没有原始聊天参与者帮助的阅读理解测试。任何环节仅能靠开发者手工改数据库、口头补背景或解释虚假成功状态才能完成，都不满足稳定版条件。

本方案及配套合同已经完成的是设计、来源核验与结构校验。它们不表示应用已经实现，不表示真实Harness连接已通过，也不表示长期科研效率提升已经得到实验证明。后续发布说明必须沿用这一证据边界。

18.2 实施前的补充核验

本轮调研没有安装并长期试用所有项目，也没有对每个依赖完成源码安全审计。准备实际复用代码时，必须补充固定提交、许可证、安装路径、数据处理位置、升级行为和最小真实任务测试。对官方接口应以目标用户实际版本验证，而不是只复述网页。

继续调研应围绕已发现的失败场景开展，例如中文短术语召回、背景解释缺失、反证传播范围、真实会话中断或大型实验清单恢复。新增工具只有在相同材料与约束下改善这些问题，且没有引入不成比例的复杂度时才进入架构。新发现如果改变领域含义、权限或数据合同，应发布新的方案版本并说明迁移。
