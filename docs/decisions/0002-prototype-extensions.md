# D-002 合同 v1.0.0 未覆盖内容在样机中的处理方式

- 状态：已采用（临时）；**进入阶段B前必须通过合同修订正式定义**
- 日期：2026-11-25
- 相关：交接包 README 第七节（合同与正文冲突必须同步修订，不能由实现者静默选择一种解释）

## 背景

方案正文要求了以下内容，但合同 v1.0.0 的 `domain.schema.json` 没有对应实体，`core-api.yaml` 也没有对应接口：

| 内容 | 方案章节 | 合同现状 |
|---|---|---|
| 项目术语表（名称、解释、正式定义、适用分支、有效修订、来源；同名不同义不合并） | §5.4 | 只有 `ReadingBrief.prerequisites`，没有独立实体 |
| 待关注事项与纠偏提醒（触发依据、来源、影响、建议、忽略或暂缓） | §6.1、§8.3 | 无 |
| 工作约定（问题、允许范围、预期产物、检查方式、可选预算） | §7.2 | `ResearchUnit.acceptance_criteria` 只覆盖一部分，没有预算 |
| 方法层与实现层的结构化内容（公式、参数、伪代码、说明与实现的映射） | §5.3 | 无 |
| 路线比较的共同维度与指标可比性分组 | §6.4 | 无 |
| 连接的采集范围与最后成功同步时间 | §6.1、§12.3 | `CapabilityManifest` 无此字段 |
| 读者偏好、隐私清除、备份恢复、导入预览、模型分析预算 | §5.4、§15.2、§15.3、§7.1、§8.4 | 无（阶段A未使用） |
| MCP 四个工具的 Schema | §12.6 | 只有工具名称 |

另外，几乎所有人工写入请求都要求非空 `grant_id`，而 `createProject` 不会签发授权，见 D-004。

## 决定

1. 合同文件保持 v1.0.0 原样，不在样机中静默修改（`npm run contracts:check` 会检查）。
2. 上表中阶段A需要的内容放在单独的扩展文件 `fixtures/stage-a/stage-a.extensions.json`，类型定义在 `fixtures/stage-a/src/extension-types.ts`，文件内明确写着“不属于合同”。界面上的术语表页也注明了这一点。
3. 扩展数据中的对象引用都由 `npm run fixtures:validate` 检查是否存在。

## 进入阶段B之前需要做的事

为合同提出 v1.1.0 修订，至少包括：术语表实体、提醒（待关注）实体、工作约定字段、连接同步状态字段、D-004 的授权起点规则，以及 MCP 工具 Schema。每项新增都要提升合同版本、补迁移说明和回归测试，并同步修订方案正文。

阶段A的理解测试结果可能会改变这些结构（例如术语卡需要哪些字段），所以建议在测试之后再定稿。
