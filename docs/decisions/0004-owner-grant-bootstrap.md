# D-004 项目所有者的第一份授权从哪里来

- 状态：**待决定**（样机暂用方案 A）
- 日期：2026-11-25
- 相关：合同 README 第五节；`core-api.yaml` 中 applyProposal、createReview、forkBranch、createCheckpoint、registerArtifact 等请求都要求非空 `grant_id`

## 问题

合同中几乎所有人工写入请求都必须引用一份授权（`grant_id` 必填且不能为 null），包括研究负责人本人记录审阅、采用决定、建立快照。但 `createProject` 只生成 Project、初始 Branch 和事件，不签发授权；`createGrant` 本身又不需要授权。于是“项目所有者本人的操作依据哪份授权”没有规定。

这不是纯技术细节：它决定了“人本人的操作”和“授权给服务自动执行的操作”在记录上如何区分，属于权限语义，按交接包要求需要产品决定。

## 候选

| 方案 | 做法 | 影响 |
|---|---|---|
| A | `createProject` 在同一事务中为创建者签发一份 `human_only`、覆盖整个项目的所有者授权 | 简单；所有人工操作都有可追溯的授权引用。需要修订合同中 createProject 的说明与验收用例。 |
| B | 人类身份的写入请求允许 `grant_id = null`，服务端以“所有者身份”为依据；只有服务代为执行时才要求授权 | 更符合直觉；但要修改多个请求 Schema，并在事件中区分“所有者本人”与“依据授权”。 |
| C | 保持现状：用户建项目后先手动建一份授权 | 不改合同；但首次使用多一步，而且容易让人误以为授权是对自己的限制。 |

## 样机中的临时做法

采用方案 A：夹具中的 `grt_owner_core` 在创建项目时生成（`human_only`，整个项目，26类动作）。界面上标注了“样机假设，见 D-004”。

## 需要研究负责人选择

请在 A、B、C 中选择，或提出其他方案。选定后需要修订合同（提升版本）并同步方案正文。
